Add the `behavioral-requirements` skill (engineering bucket, model-invoked). It maintains the **behavioral contract**: the persistent statement of what the system must do, one stable ID per rule, in the project's own vocabulary. Four artifacts answer four different questions and each keeps its own file: the contract answers what must be true, `CONTEXT.md` what the words mean, the ADRs which hard decisions were made, the spec how we will build it. The contract is authoritative for expected behavior, so where the code and a rule disagree the disagreement is the finding and the rule is reported rather than edited, which is what makes the layer a drift detector rather than a second description of the code. The skill locates the contract from the repo's agent configuration, asking once on a repo's first run and recording the answer so later runs read it. `grilling` calls it as a session closes, and it classifies each settled decision by kind (behavior, term, architectural decision, build plan, rejected possibility), so a session that settled architecture rather than behavior writes nothing. `to-spec` and `to-tickets` call it to load the applicable rules and cite their IDs, referencing them by ID rather than restating each rule as a user story, which is what stops the spec becoming a third behavioral specification.
